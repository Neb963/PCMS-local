## Objective

Resume provisioning verification/challenge flows through durable HumanTasks, activate an Account only after the authenticated provider identity matches the staged identity, and recover interrupted signup/login read-first without blindly creating a duplicate remote account.

## Implemented

- T039.1 — extended the deterministic Perchance provisioning surface with explicit CAPTCHA and verification-code states plus bounded continuation references. The browser flow returns structured human-required outcomes rather than treating these states as generic provider failure.
- T039.1 — added provisioning-specific HumanTask continuation over the existing `HumanTaskStore` and `HumanContinuationService`. CAPTCHA completion reuses the same Persona/page and logical operation. Verification codes are accepted only as process-local expiring one-time input, consumed once by continuation, and are absent from task evidence and emulator request evidence.
- T039.2 — added authenticated provider-identity verification to `ProvisioningBrowserFlow` and a fenced `AccountRepository.activateVerified` transition. Provisioning keeps the Account INACTIVE through signup/challenge handling and can set ACTIVE only after the current authenticated session identity matches the operation's expected provider identity and the dedicated Persona binding/revision remain valid.
- T039.2 — added `ProvisioningOperationService` as a thin provisioning-specific coordinator over the existing Core OperationCoordinator, ProviderGate and HumanTask mechanisms. Durable operation provenance stores the expected provider identity and an opaque credential reference, never raw password or verification-code bytes.
- T039.3 — added read-only provider identity existence probing and read-first interrupted-flow reconciliation. An ambiguous signup first checks authenticated session state and remote identity existence; if the account exists, recovery logs in instead of redispatching signup. An ambiguous login is reconciled by a subsequent authenticated-session read before any further mutation.
- T039.3 — added deterministic response-loss emulator behavior that commits signup, withholds the signup response, then commits login while withholding its body. Real-Chromium acceptance proves exactly one signup and one login request, identity/session reads between ambiguous effects, successful activation, and no duplicate account-creation retry.

## Deviations / ADRs

No ADR change was required.

P039 reuses the generic durable OperationCoordinator and HumanTask continuation semantics established in P027/P028 instead of creating a second workflow engine. Provisioning-specific continuation descriptors remain explicit and bounded.

Recovery persists only non-secret intent needed to reconstruct the flow: expected provider identity plus an opaque credential reference. The credential resolver supplies the password transiently when a login continuation is actually required; password bytes never enter ordinary operation provenance.

Account activation is a separate, optimistic repository transition so the provisioning service cannot make an Account operational merely because signup returned success. If local activation succeeded before a later process interruption, the activation primitive is idempotent for the same Persona, while remote identity is still re-read during operation reconciliation.

- Provider-side challenge semantics beyond the bounded CAPTCHA/verification-code contract remain fail-closed and require human attention rather than automated bypass.
