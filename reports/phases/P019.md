## Objective

Prove that supported protected Chromium networking does not silently escape the selected synthetic route when DNS, QUIC, WebRTC or protected-forwarder loss is exercised.

## Implemented

- T019.1 centralized protected Chromium network policy in BrowserManager: SOCKS5-only protected URL proxying, catch-all destination resolver blocking with loopback control exceptions, QUIC disabled, and WebRTC non-proxied UDP disabled through both launch configuration and persisted Chromium profile preferences.
- T019.1 added real Chrome network canaries. The synthetic SOCKS endpoint proves destination hostnames arrive unresolved, while a controlled UDP STUN endpoint and ICE observation verify that the protected browser emits no non-proxied WebRTC UDP.
- The first WebRTC canary caught a real defect: Chrome 154 still emitted STUN UDP with the command-line WebRTC setting alone. BrowserManager was corrected to set Chromium's profile WebRTC preference before protected launch; the unchanged canary then passed.
- T019.2 added fault injection that establishes healthy protected egress, stops the active synthetic SOCKS forwarder while Chromium remains running, and proves the subsequent protected request fails.
- T019.3 added independent Direct/control-path checks after route loss. A non-loopback HTTP endpoint is proven reachable from the runner, yet receives no protected-browser request after proxy loss. A separate loopback control endpoint remains reachable as the intentional local-control exception.
