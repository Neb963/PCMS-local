## Objective

Complete routing-mode semantics for explicit Direct and Block operation, protected-route switching, and multiple simultaneously active protected Personas using deterministic real-Chromium and synthetic-network evidence.

## Implemented

- T020.1 — added `ChromiumRoutingManager` as the explicit Core routing coordinator. Supported launches must state `DIRECT`, `BLOCK`, or `PROTECTED`; a missing/unknown mode is rejected at runtime.
- T020.1 — Direct sessions are visibly classified `DIRECT`, carry no route ID, and expose mutation admission only because Direct was explicitly selected.
- T020.1 — Block sessions are visibly classified `BLOCK`, deny mutation admission, and own a dedicated IPv4-loopback blackhole guard. BrowserManager receives that endpoint through the already-hardened proxy path, so external Chrome traffic cannot silently become Direct while Block remains diagnostically distinct from a protected route.
- T020.1 — real Chrome acceptance independently proved the external HTTP canary reachable, then proved Direct reached it and Block did not.
- T020.2 — protected route switching is process-safe: mutation admission is blocked during transition, the old protected browser/lease closes first, the replacement route uses the existing P018/P019 preflight + real-browser egress verification, and admission reopens only after the replacement protected launch has completed successfully.
- T020.2 — real Chrome acceptance switched one Persona from synthetic alpha to beta, observed a new Chromium PID, verified beta preflight/browser egress, and proved the router command order was prepare-alpha → release-alpha → prepare-beta.
- T020.3 — real Chrome acceptance kept two protected Personas active simultaneously on separate PIDs, profile roots, DevTools ports and synthetic exits. Independent CDP probes observed alpha only through alpha and beta only through beta, with no cross-exit observation.

## Deviations / ADRs

No ADR change was required.

Block mode uses a coordinator-owned loopback blackhole endpoint rather than pretending a failed protected route is Block. This preserves the architecture distinction: intent/diagnostics are explicitly `BLOCK`, while BrowserManager reuses the already-proven hardened proxy mechanics to prevent external fallback.

## Known issues / unknowns

- Real Mullvad/WireGuard interoperability remains final live acceptance in P048–P049.
- The coordinator is the supported explicit routing surface. Low-level BrowserManager remains a mechanism used by earlier browser/runtime tests and is not itself the route-policy API.
- Protected switching in this phase is PROTECTED→PROTECTED. Direct and Block are explicit launch modes; broader operator policy/orchestration can build on these typed primitives later without changing M04 acceptance.
- The routing guarantees are empirical for the supported Chromium configuration plus controlled synthetic fixtures, not a kernel-enforced isolation claim.
