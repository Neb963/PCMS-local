## Objective

Create stable Persona user-data directories and explicit open/close/retire/delete guards.

## Implemented

- T012.1 — added the dedicated PCMS Persona root under the data root and a Core-owned `PersonaProfileLifecycle` backed by the authoritative SQLite database. Each Persona UID maps deterministically to `personas/<personaUid>/chromium`; unsafe identifiers, symlink escapes, incompatible non-empty directories and ownership-marker mismatches fail closed.
- Added migration `0005-persona-profile-lifecycle` with durable Persona lifecycle/profile state, backend identity, relative profile path, revision, retirement metadata, backup decision and staged/deleted profile state. Browser profile bytes remain outside SQLite.
- Existing Persona records never silently recreate a missing profile. Once a durable Persona/profile association exists, a missing or incompatible owned root is surfaced as an error rather than replaced with a fresh browser identity.
- T012.2 — added explicit open/close persistence semantics. Open marks the persistent root active; close records CLOSED without removing profile bytes; reopening resolves the same owned root and preserves sentinel state.
- T012.3 — added non-destructive retirement and guarded destructive deletion. Retirement requires CLOSED state. Deletion requires explicit confirmation, confirmed browser closure, zero unresolved Operation/HumanTask evidence, an explicit backup decision, RETIRED+CLOSED lifecycle state and deterministic path/ownership validation.
- Destructive deletion is staged durably before filesystem removal using `PRESENT → DELETE_STAGED → DELETED`. Retry can reconcile the case where bytes were removed after durable intent but before metadata finalization; staged/deleted profiles cannot be reopened or silently recreated.
- Added deterministic filesystem/SQLite integration coverage for traversal/symlink refusal, incompatible directory refusal, persistent close/reopen state, missing-profile refusal, retirement guards, deletion guards, tampered-path protection and interrupted staged-delete reconciliation.
- Updated existing daemon/control-surface/bundle integration assertions to derive the database schema version from `CORE_MIGRATIONS.length` rather than hardcoding version 4.

No provider login, routing, real Chromium process launch, generic CDP automation or MCP behavior was added. Those remain owned by later M03 phases.

## Deviations / ADRs

No architecture deviation and no new ADR.

The implementation records profile deletion intent before removing filesystem bytes. This directly implements the architecture's staged-destructive-operation requirement and makes retry/recovery explicit rather than treating a filesystem/SQLite split-brain as success.
