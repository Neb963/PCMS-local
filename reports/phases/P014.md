## Objective

Make browser runtime ownership and recovery safe across pcmsd/BrowserManager loss or Chromium loss, refuse ambiguous profile attachment, and enforce a bounded active-Persona count without disrupting existing human work.

## Implemented

- T014.1 — added persisted Chromium runtime ownership evidence in SQLite. A runtime record carries the Persona UID, STARTING/RUNNING/DEGRADED state, PID, Linux process-start fingerprint, configured and canonical executable paths, browser version, profile ownership through the exact `--user-data-dir` argument, profile-scoped DevTools port/path, timestamps and bounded diagnostic detail.
- Added migration `0006-persona-browser-runtime` with foreign-key ownership to the durable Persona row and integrity checks requiring complete process/DevTools evidence before a runtime can be RUNNING.
- Browser ownership validation uses Linux `/proc/<pid>/stat`, `/proc/<pid>/exe` and `/proc/<pid>/cmdline`; PID alone is never treated as identity. Before any signal is sent to a reconciled process, the process fingerprint is revalidated.
- Unsafe attach/relaunch is fail-closed. An OPEN profile without matching runtime evidence, a PID/start/executable/profile mismatch, or a live unowned profile-scoped DevTools endpoint produces `PERSONA_BROWSER_OWNERSHIP_AMBIGUOUS` and does not start a second browser.
- T014.2 — added `reconcile` / `reconcileAll`. A fresh BrowserManager can reconnect to a still-running Persona only after persisted process/profile/DevTools ownership is re-proven. A gone process clears stale runtime state and returns the Persona profile to CLOSED. An alive but unverifiable runtime becomes DEGRADED rather than being guessed healthy.
- Browser child exit now reconciles a Chromium crash back to CLOSED while preserving the durable Persona/profile root. Reopening the same Persona reuses the same profile path with a new process.
- Reconciled close first requests CDP `Browser.close`; bounded SIGTERM/SIGKILL escalation is permitted only while the persisted fingerprint still identifies the same process.
- T014.3 — added configurable `maxActivePersonas` admission control (default 8, validated range 1–128). Capacity is computed after reconciliation and excess launches fail with `PERSONA_BROWSER_CAPACITY_EXCEEDED`; existing sessions are left untouched.
- Added real-Chromium recovery acceptance covering safe fresh-manager reconnect, SIGKILL crash/reopen, ownership tamper refusal, a cap of one with 52 dormant Persona profiles, and preservation of the already-running Persona when excess work is rejected.

No routing, provider automation, generic external DevTools-client acceptance or MCP behavior was implemented.

## Deviations / ADRs

No architecture deviation and no new ADR.

Runtime process fingerprinting is Linux-specific because the supported v0.1/Fedora target and GitHub Ubuntu CI expose the necessary `/proc` evidence. This follows architecture 03's requirement to validate process executable/profile/start identity rather than trust a PID.

The cap currently rejects excess admission rather than introducing a scheduler queue. A03-10 explicitly permits queue or reject; scheduler/priority policy remains owned by later scheduling phases.

## Known issues / unknowns

- A reconciled runtime with valid process ownership but unavailable/mismatched DevTools evidence is deliberately DEGRADED/fail-closed; P014 does not invent automatic browser replacement.
- STARTING state that survived a daemon crash before a process fingerprint was persisted can only be cleared when no live profile DevTools endpoint exists; if a live endpoint is present without enough process evidence, ownership remains ambiguous and requires operator/recovery handling rather than unsafe attach.
- Generic external DevTools attach/interact/detach behavior is not accepted here. P015 owns A03-08.
- Routing, provider behavior and MCP interoperability remain later phases; final live MCP acceptance remains P048–P049.
