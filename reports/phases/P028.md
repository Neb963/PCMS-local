## Deviations / ADRs

No ADR change was required.

The response-loss emulator originally used a TCP reset after committing the effect. Real Chromium demonstrated that this transport fault may trigger browser-level POST replay, so it was not a valid deterministic model for proving PCMS no-redispatch behavior. The fixture was changed to commit the effect and withhold the response until the already-bounded BrowserDriver command times out. This preserves the intended ambiguity while ensuring the emulator itself does not create a duplicate request.

ProviderGate uses process-local active-concurrency permits and durable cooldown observations. This matches the single-authority pcmsd topology: concurrency permits represent current process liveness, while externally meaningful rate-limit/challenge/outage state must survive restart.

Human continuation descriptors are data, not serialized functions. One-time verification input is intentionally ephemeral and may require re-entry after restart; durable HumanTask state remains the authoritative record that operator action is still required.

## Known issues / unknowns

- P028 provides generic reconciliation and continuation mechanisms; feature-specific deployment/provisioning policies remain assigned to later phases.
- ProviderGate does not queue work or implement scheduler/backoff policy. P029 and later module phases own those semantics.
- HumanTask continuation does not automate CAPTCHA solving or challenge bypass. Human completion is external/operator-driven.
- The Perchance challenge expression is an explicit compatibility profile input. Current real Perchance challenge shape is not claimed until final live acceptance.
- Exactly-once external mutation is still not claimed; read-first reconciliation and durable target claims prevent blind duplicate dispatch within the supported contract.
- Live Perchance/browser-agent interoperability remains P049 acceptance.
