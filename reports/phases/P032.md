## Objective

Make repeated Deployer synchronization safe under already-matching provider state, changed artifacts, stable-target drift, and ambiguous save response loss, without blind redispatch.

## Implemented

- T032.1 — changed deployment execution to read current provider state before creating a mutation operation. Exact stable ID, slug, artifact SHA-256, file content and required public state produce a true `NO_OP`: no save request and no new OperationCoordinator row.
- T032.1 — changed content or public state follows the existing durable OperationCoordinator path and performs a bounded update. Provider observations now permit an empty pre-deployment file set while desired deployments still require non-empty validated content.
- T032.1 — current-state reads fail closed. Deployer does not infer a no-op or dispatch a write when current provider state cannot be verified.
- T032.2 — added real-Chromium/emulator regression coverage proving provider stable-ID replacement and old-slug reuse cannot redirect a mutation. Both cases are rejected by the stable GeneratorRef resolver before deployment read/save.
- T032.3 — added bounded OperationCoordinator lookup by idempotency key so the same durable logical operation can be recovered without reconstructing a fresh mutation intent or weakening precondition equality.
- T032.3 — ambiguous mutation loss is recorded as `UNCERTAIN` and immediately enters the existing `OperationReconciler` read-first path. Exact desired provider state resolves the same operation to `SUCCEEDED`; a mismatch/read failure remains unresolved and automatic redispatch is blocked.
- T032.3 — repeated calls with the same idempotency key recover the existing durable operation. A reconciled-success operation is re-read and returns `NO_OP` only if desired state is still present; it is never sent again merely because the original response was lost.
- T032.3 — known non-dispatch rejection remains `FAILED_SAFE`; it is not reclassified as an ambiguous effect.

## Deviations / ADRs

No ADR change was required.

P032 reuses the existing OperationCoordinator/OperationReconciler uncertainty model rather than adding Deployer-specific retry state. A response loss that may follow a committed effect therefore remains `UNCERTAIN` until an independent provider read proves the desired effect.

A provider-state mismatch during reconciliation is intentionally treated as `UNKNOWN`, not `CONFIRMED_NOT_APPLIED`. The observed mismatch does not prove that the ambiguous save never occurred; another change could have happened afterward. This conservative interpretation preserves the no-blind-retry invariant.

The idempotency lookup is exposed as a narrow read method on OperationCoordinator. It does not allow callers to rewrite durable operation identity, preconditions, target claims or outcome state.

## Known issues / unknowns

- P032 does not implement polling, module package lifecycle/update/rollback or the complete Account→Persona→synthetic-route→emulator vertical slice; P033 owns those.
- If ambiguous outcome reconciliation cannot read provider state or reads a non-matching state, the operation remains unresolved and automatic redispatch is blocked.
- A completed idempotency key cannot be silently reused after provider state drifts away from its recorded desired intent.
- Emulator evidence is deterministic CI evidence, not proof of current live Perchance compatibility. Live compatibility remains P049.
