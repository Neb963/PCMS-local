## Objective

Create namespaced module state, runtime-generation fencing and safe candidate-state migration.

## Implemented

- T008.1 — added Core-owned SQLite module registration/state-generation tables through immutable core migration `0002-module-state-generations`. Each module has an active version/state generation, state schema version, state revision, authoritative runtime generation and enabled flag. Module state is namespaced by module/generation, JSON-only and bounded by key/value/entry/aggregate byte limits.
- Added scoped `storage.get`, `storage.set` and `storage.delete` SDK handlers. Module code receives serialized values only; no raw SQLite handle is exposed. Active writes re-check the runtime generation and advance the state revision.
- Extended the runner with a per-SDK-request Core authorizer so authoritative runtime generation/enabled state is checked before any approved handler is invoked. Advancing the generation fences an old process; disabling advances the generation and denies the current disabled generation as well.
- T008.2 — added candidate-state preparation from a frozen active snapshot. Migration and health callbacks receive bounded state and have bounded execution time. Candidate output is normalized/bounded and persisted as `READY_TO_SWITCH` only after migration and health succeed.
- Candidate preparation records its base active generation/revision and rechecks them before persistence. If active state changes concurrently, candidate commit fails closed with `MODULE_ACTIVE_STATE_CHANGED`.
- Migration/health failure, timeout or invalid/oversized migrated state persists no candidate generation and never switches or mutates the active version/state.
- T008.3 — added real module-runner integration proving an SDK call succeeds before fencing, the same process receives structured `MODULE_RUNTIME_STALE` after generation advance/update fencing, and SDK calls remain denied after disable. Underlying Core handlers are not invoked by stale/disabled runtimes.
- Review hardening added aggregate entry/byte enforcement to incremental active-state writes, preventing repeated `storage.set` calls from bypassing registration/migration state bounds.

No capability-delta approval, candidate activation transaction, rollback/remove lifecycle, package update fetching or module UI was implemented.

## Deviations / ADRs

No architecture deviation and no new ADR.

Candidate migration executes through a narrow bounded callback interface over a frozen JSON snapshot. The supported interface provides no DB/router/CDP/SDK authority to migration logic; determinism remains a module contract under the documented operator-trusted same-user code model rather than an adversarial sandbox guarantee.

The P008 schema stores candidate base state generation/revision so P009 can atomically verify that a prepared candidate still derives from the current active state before switching it.

## Known issues / unknowns

- P008 deliberately does not activate `READY_TO_SWITCH` candidates. P009 owns capability-delta approval and the atomic transaction that changes active version/state/runtime generation.
- P008 does not implement rollback, disable/re-enable lifecycle persistence beyond the runtime generation/enabled authority, remove/purge, package update acquisition or module UI; later M02 phases own those behaviors.
- Module state values are intentionally bounded JSON. Large artifacts must remain referenced rather than stored inline, consistent with the architecture.
