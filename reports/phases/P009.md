## Objective

Require explicit authority-delta approval and atomically activate only validated candidates.

## Implemented

- T009.1 — added canonical module authority envelopes derived from validated manifest capabilities plus required module-service dependencies. Provided services are not treated as consumed authority. Initial authority computes as a delta from the empty envelope; updates deterministically report added/removed capabilities and required services.
- Authority envelopes and deltas are normalized, sorted, bounded, validated and canonically serialized for durable audit records.
- T009.2 — added core migration `0003-module-authority-activation`. The active module registry now stores the approved authority envelope and activation timestamp; every state generation can store requested authority, exact delta, approval state, decision timestamp and activation timestamp.
- Existing active registrations are migrated conservatively with an empty approved envelope. New active registrations can record an already-approved initial envelope and corresponding generation audit record.
- Candidate authority expansion is staged as `AWAITING_APPROVAL`; equal or reduced authority is `NOT_REQUIRED`. Explicit approve/decline transitions are durable.
- Atomic candidate activation runs in one `BEGIN IMMEDIATE` transaction. It rechecks candidate readiness and base state generation/revision, rejects pending or declined expansion, retains the prior state generation, promotes the candidate to ACTIVE, switches active version/state schema/state generation/approved authority, resets the new generation state revision, increments runtime generation, and records activation metadata.
- The runtime-generation increment fences the pre-switch process immediately; derived process reconciliation remains outside the DB transaction.
- T009.3 — integration tests cover expansion-before-approval refusal, explicit approval and successful switch, decline refusal, reduced authority without a new approval, equal authority without a new approval, and stale-candidate rejection with the old active version/state/runtime generation preserved.

No disable/re-enable lifecycle, rollback execution, remove/purge handling or module UI was implemented.

## Deviations / ADRs

No architecture deviation and no new ADR.

`registerModule(..., initialApprovedAuthority)` accepts an already-approved initial envelope because P008 registration represents an existing active registration rather than the package-install approval workflow. The authority helper still computes initial requested authority as expansion from the empty envelope; future install orchestration must obtain explicit approval before supplying non-empty initial approved authority.

## Known issues / unknowns

- P009 does not stop/start module processes around the transaction; runtime-generation fencing makes old processes stale and later lifecycle reconciliation owns process transitions.
- P009 retains prior package/state generation metadata for rollback but does not execute rollback. P010 owns rollback via a new generation.
- P009 does not implement disable/re-enable, remove/purge or unresolved-operation/HumanTask guards; P010 owns those controls.
