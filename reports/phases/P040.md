## Objective

Complete Explorer/Provisioning operational isolation, independently exercise both first-party module package lifecycles, and prevent sensitive transient provisioning input from entering ordinary durable/module/error surfaces.

## Implemented

- T040.1 — added single-child cancellation to the existing generic `BatchStore` without creating a second authoritative state machine. Each child still resolves through its durable `OperationCoordinator` record; terminal children remain unchanged and cancellation after dispatch follows the existing UNCERTAIN doctrine.
- T040.1 — added `ProvisioningBatchService`, a provisioning-specific projection that validates each child as a complete `provisioning.account` operation and exposes isolated per-account Account/Persona/provider-identity/opaque-credential-reference input, current operation state, result and cancellation accounting. Duplicate Account membership is rejected before durable batch creation.
- T040.2 — added deterministic Explorer and Account Provisioning `.pcmsmod` fixtures and lifecycle acceptance through the standard `ModuleManager` path. Updating or rolling back either module changes only that module's version/runtime generation and preserves the other module's active version/generation/state.
- T040.3 — audited the sensitive-input path and found arbitrary exception text crossing module RPC and module-UI SDK error boundaries. Hardened module→Core backend errors, Core→module SDK handler errors and module-UI SDK HTTP errors to preserve bounded error codes/retryability while replacing untrusted exception text with generic messages.
- T040.3 — added regression coverage proving module-thrown and Core-handler sensitive sentinels are not echoed across those boundaries.
- T040.3 — added a durable-data-root audit: one-time verification input is submitted through `HumanTaskStore`, safe operation/module records are written, then persisted rows and every file under the temporary PCMS root are scanned to prove the raw sensitive value was never serialized.

## Deviations / ADRs

No ADR change was required.

The per-account provisioning batch is intentionally a projection over existing durable child operations rather than a new batch-specific operation state machine. This preserves P029's invariant that child operations are authoritative and prevents aggregate batch state from becoming a competing truth source.

The provisioning batch exposes an opaque credential reference because restart-safe provisioning already requires that reference; it never stores or exposes credential bytes.

The redaction change preserves bounded machine-readable error codes while removing exception text at untrusted boundaries. Trusted validation errors generated by Core itself remain specific where they do not contain caller-controlled sensitive values.
