## Objective

Provide bounded batch and scheduler primitives without replay storms, cross-child result corruption, or a generic workflow engine.

## Implemented

- T029.1 — appended migration `0012-batches` with durable batch membership and per-child cancellation accounting while keeping each child OperationCoordinator record authoritative for actual result/state.
- T029.1 — added `BatchStore` projection semantics over independent child operations. Aggregate status/counts are derived from current operation states rather than copied into a second mutable source of truth.
- T029.1 — batch cancellation requests cancellation only from unresolved children through OperationCoordinator. Already-terminal SUCCEEDED/FAILED_SAFE/CANCELLED children remain unchanged; dispatched RUNNING/VERIFYING children retain existing UNCERTAIN cancellation doctrine.
- T029.1 — cancellation accounting is per child and error-isolated so one cancellation race/error does not prevent the batch from recording or attempting the remaining children.
- T029.2 — appended migration `0013-schedules` with schedule owner/reference metadata, UTC next-due state, explicit timezone, priority/fairness key, one durable pending dispatch intent, last dispatched/terminal operation references, bounded failure code, and optional persisted window budget.
- T029.2 — added `BoundedWorkQueue` with finite capacity, structured retryable overflow, duplicate-key coalescing, priority lanes, same-priority fairness rotation, deadlines, cancellation and in-flight accounting.
- T029.2 — added `DurableScheduler` wake semantics: timers are hints; each wake reloads durable state, reuses an existing pending dispatch ID when present, advances next-due and budget atomically with a newly persisted dispatch intent, and emits at most one current intent per due schedule.
- T029.2 — wall-clock rollback uses the persisted maximum observed clock and cannot reopen a budget window early. Forward jumps reset an elapsed budget window once and advance next due from the current effective instant instead of replaying every missed interval.
- T029.2 — schedule budget use is charged when the durable dispatch intent is created, not when the in-memory queue happens to deliver it. This is conservative across crashes.
- T029.3 — restart/backpressure acceptance proves queue loss does not lose a pending durable dispatch: a new scheduler instance reconstructs the same dispatch ID from SQLite.
- T029.3 — when the bounded queue is full, additional due schedules remain due and do not mint durable pending intents or consume budget. Once capacity returns, one current intent is created; no missed-work backlog is materialized.
- T029.3 — abandoning an in-process claim drops only the in-memory claim. The next wake requeues the same persisted dispatch ID rather than minting a new mutation identity.

## Deviations / ADRs

No ADR change was required.

Batch result state is intentionally not duplicated into a mutable batch-owned state machine. Child operations remain authoritative and the batch derives aggregate state from them. This directly preserves the architecture rule that partial batch failure cannot corrupt an already-successful target.

Scheduler dispatch identity is persisted before in-memory delivery. The in-memory queue can disappear on restart; the durable schedule row remains the recovery source. A consumer should use the dispatch ID as the child operation idempotency key so re-delivery of the same pending intent remains duplicate-safe.

The generic P029 budget is a rolling persisted window primitive. Module-specific active/sleep/local-calendar/DST policy remains owned by later feature phases, especially P035.

## Known issues / unknowns

- P029 implements fixed-interval Core scheduling primitives, not cron or a universal workflow language.
- Timezone is stored and validated now; local-calendar/DST scheduling policy is intentionally deferred to the module policy phase that owns A08-04.
- Queue fairness uses caller-provided bounded fairness keys with priority-class ordering. Feature modules remain responsible for choosing account/module grouping appropriate to their policy.
- A durable pending dispatch can be re-delivered after process loss; exactly-once execution is not claimed. Its stable dispatch ID is the idempotency boundary.
- Scheduler does not blindly retry UNCERTAIN operations; retry/reconciliation policy remains with OperationCoordinator and feature modules.
- No live provider, MCP or Mullvad dependency was introduced.
