## Objective

## Implemented

- T043.1 — added a read-only Attention projection over the existing durable `human_tasks` source of truth. The integration acceptance creates an open HumanTask, verifies API/CLI/Web visibility, restarts `pcmsd`, and proves the same task remains open and visible.

The test exposed that P042 copied backed-up `.pcmsmod` archives without rebuilding their extracted immutable runtime trees. Restore now reconstructs each validated module artifact through the existing `ModulePackageStore` during staging, so the restored active package is loadable as well as present.
- T043.3 — added `docs/implementation/v0.1/FULL_V1_GAP_LEDGER.md`, updated specification traceability, and added a roadmap Full-V1 claim gate. All 18 PRD §24 requirements are classified explicitly as IMPLEMENTED, PARTIAL or DEFERRED. Partial/deferred requirements remain binding post-v0.1 Full-V1 work and cannot be silently relabeled complete by M11/M12 hardening.

## Deviations / ADRs

No PRD requirement was removed or weakened. P043 made the explicit release-scope decision already delegated to it by `SPEC_TRACEABILITY.md`: the v0.1 roadmap is a hardening/acceptance baseline, not a Full-V1 completeness claim. The gap ledger records the unresolved requirements and their dispositions; no separate ADR was required because the existing implementation traceability explicitly authorized a ledger/roadmap amendment for this decision.

No live Perchance, Mullvad or MCP dependency was introduced.

## Known issues / unknowns

The Full-V1 ledger intentionally remains non-empty. The broader Project model, workspaces/revision history, first-class deployments linked to revisions, reusable Workflow definitions/Runs, notifications, and full cross-entity global search remain PARTIAL or DEFERRED. M11/M12 may harden and validate v0.1 but cannot describe it as Full V1 unless a later roadmap/product decision closes those rows.

Restored provider-owned state still follows the P042 recovery contract: external state is unknown until reconciled and restore remains in `RECOVERY_HOLD` until explicitly released.
