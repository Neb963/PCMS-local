## Objective

Create the narrow BrowserDriver over already-running Persona Chromium processes without creating automation-only browser identities or implementing Perchance semantics.

## Implemented

- T025.1 — added a typed Core `BrowserDriver` that resolves the existing owned Persona through `ChromiumBrowserManager.resolveDevToolsEndpoint`, connects to its profile-scoped loopback browser WebSocket, lists page targets, selects a requested page target and evaluates bounded browser-side expressions. BrowserDriver has no launch path and cannot request a new Chromium user-data directory.
- T025.1 — recorded the exact M06 browser automation compatibility baseline: Node.js 24.21.0 plus Chrome for Testing 154.0.8037.92. The implementation uses a narrow internal CDP-over-WebSocket transport instead of adding Puppeteer dependency surface; raw CDP remains internal to Core.
- T025.2 — bounded the complete attach path, including owned-endpoint resolution and WebSocket connection, and added per-command deadlines plus `AbortSignal` cancellation. Structured errors distinguish Persona-not-running, connect failure/timeout, cancellation, command timeout, connection loss, protocol failure, target-not-found and target-loss cases.
- T025.2 — added `BrowserDriverEffectState` so failures before dispatch are explicitly `NOT_DISPATCHED`, while timeout/cancellation/protocol or transport loss after a browser command was dispatched is `MAY_HAVE_OCCURRED`. Later mutation coordination can therefore reconcile ambiguous external effects rather than treating cancellation as rollback.
- T025.3 — added real Chrome acceptance proving BrowserDriver attach/detach preserves the same Persona PID, profile directory set, runtime row, DevTools endpoint and OPEN lifecycle state. No second profile/runtime/browser identity is synthesized.
- T025.3 — added real Chrome target-loss injection by closing the selected target from an independent root CDP connection and proving subsequent driver work returns structured `BROWSER_DRIVER_TARGET_LOST` while the Persona browser remains alive.

## Deviations / ADRs

No ADR change was required.

Architecture 05 permits `puppeteer-core` **or a comparable CDP client** behind BrowserDriver. P025 uses the repository's Node runtime WebSocket implementation and the already-proven browser-level CDP endpoint instead of adding a new dependency. This keeps the seam narrow and avoids dependency churn while preserving the architectural rule that modules/provider policy do not receive raw CDP authority.

The compatibility matrix required before M06 browser automation work is recorded in `docs/research/browser-automation-baseline-2026-10-03.md`.

## Known issues / unknowns

- P025 deliberately does not implement Perchance session/generator semantics or the emulator; P026 owns those capabilities.
- A timeout or cancellation after a browser command has been dispatched is reported as `MAY_HAVE_OCCURRED`; callers performing future provider mutations must reconcile instead of blindly retrying. Durable mutation state/claims remain owned by P027.
- Passing pinned real-Chrome CI proves the encoded browser contract, not current live Perchance/MCP compatibility. P048–P049 remain the live acceptance phases.
