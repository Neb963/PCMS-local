## Objective

Create the stateful evidence-backed Perchance emulator and use it through real Chromium/provider-adapter identity probes, without making CI depend on live Perchance or turning unverified provider behavior into fact.

## Implemented

- T026.1 — added a reusable loopback Perchance emulator with isolated account/session/generator state, ASCII case-insensitive account matching for the verified compatibility profile, mutable generator slug/stable-ID test state, bounded request parsing, and secret-safe request evidence.
- T026.1 — added deterministic named fault scenarios for unknown application status, malformed success payload, non-JSON perimeter blocking and HTTP failure. These are explicitly documented as synthetic failure injection rather than live-provider assertions.
- T026.1 — recorded the evidence boundary in `docs/research/P026-PERCHANCE-EMULATOR-EVIDENCE.md`: the 2026-09-28 predecessor discovery is provenance input only; non-zero owned-generator response shape and endpoint-specific invalid-pair behavior remain emulator modeling assumptions pending P049.
- T026.2 — added a read-only `PerchanceProvider` that executes through `BrowserPage` from the existing BrowserDriver. The trusted compatibility expression may discover page-held session material, but the adapter wrapper consumes the session token entirely inside the provider page and returns only normalized, non-secret evidence to Core.
- T026.2 — implemented expected/mismatch/unknown session identity outcomes, fail-closed handling for provider protocol drift/perimeter/HTTP failures, and bounded normalization of current generator slug plus preferred stable `publicId` identity.
- T026.2 — implemented GeneratorRef revalidation semantics that distinguish stable-ID verification from mutable-slug drift. Stable ID can remain VERIFIED while slug becomes CHANGED; same-slug/different-stable-ID is an identity MISMATCH; absent stable identity remains UNKNOWN rather than being inferred from a slug.
- T026.3 — added real-Chromium BrowserDriver acceptance that launches the already-owned Persona browser at the emulator, exercises expected/mismatched/missing sessions, protocol/perimeter uncertainty, generator rename and stable-ID replacement, and proves stale evidence is classified separately from current evidence.
- T026.3 — added deterministic integration coverage for emulator state/fault scenarios and assertions that stored test evidence does not retain synthetic session tokens.

## Deviations / ADRs

No ADR change was required.

The provider adapter deliberately accepts a trusted browser compatibility expression rather than hard-coding a current Perchance page-store implementation. This preserves the architecture boundary: provider-specific page details stay in compatibility artifacts while Core receives semantic read evidence. The expression is not a module/user input and does not expose its page-held session token in adapter output.

## Known issues / unknowns

- The emulator's non-zero generator list shape is intentionally a compatibility model, not a claim about current live Perchance. P049 owns final live verification.
- Invalid email/session pairing on `getGeneratorsByUser` is modeled from equivalent pairing rejection observed on `checkGeneratorOwnership`; endpoint-specific live behavior remains unverified until P049.
- Current real Perchance page/session-store extraction details remain outside P026. P026 proves the provider-adapter seam using a deterministic trusted browser artifact.
