## Objective

Create the supported Fedora/Linux install, update and uninstall path without requiring end-user npm/pnpm setup, while preserving user state unless destructive purge is explicit.

## Implemented

- T044.1 — extended the existing self-contained release bundle with a verified installer, managed content-addressed release tree, atomic `current` switch, `~/.local/bin/pcms` and desktop launcher integration, and the existing hardened systemd user service. The desktop launcher starts `pcmsd`, reads the authenticated local origin through the CLI diagnostics path, and opens the same-origin Web UI without embedding the API token in the desktop file or URL.
- T044.2 — made rerunning the verified bundle installer the Core update path, retaining prior releases and health-checking the newly selected release. Compatible-schema health-check failure restores the previous release pointer. Added `pcms-uninstall`/bundle uninstall entrypoints: default uninstall removes application/service/desktop integration and preserves PCMS data, Persona profiles and router configuration; destructive PCMS user-data removal requires both `--purge-data` and `--yes`. Privileged router configuration is never removed by this unprivileged command.
- T044.3 — added a Fedora 44 container CI gate that builds the self-contained bundle and runs the clean-user install/update/desktop/uninstall lifecycle acceptance. The aggregate CI gate now requires this Fedora install job.

## CI evidence

Failures found during P044 were fixed rather than bypassed:

- Repository verification initially rejected marking M11 IN_PROGRESS before any constituent phase was complete; phase-state records were corrected to the repository's derived milestone rule.
- The first installed CLI acceptance exposed that invoking `~/.local/bin/pcms` through a symlink caused the launcher to resolve `~/.local/runtime/node`. Managed launchers now use the known install root while direct bundle launch remains independent of system PATH tools.
- A follow-up fix using external `readlink` broke the existing bundle lifecycle test under an intentionally restricted PATH. The launcher was rewritten to avoid that external dependency.
- The purge fixture initially inherited the runner's XDG environment and therefore asserted against different roots than PCMS actually resolved. The clean-home fixture now explicitly binds XDG config/data/cache roots to its temporary HOME.
- One P028 browser/emulator test transiently failed during `Runtime.evaluate` on the first Fedora-job PR run. The P044 Fedora lifecycle and all other jobs were green; rerunning the failed browser job passed without code changes. Final implementation-head CI #688 passed cleanly.

## Deviations / ADRs

No architectural redesign was introduced. P044 extends the existing P005 bundle and systemd service contracts rather than adding a second packaging path. The update path is content-addressed and checksum-verified; package signing remains deferred exactly as defined by the installation/release architecture.

No live Perchance, Mullvad or MCP dependency was introduced.

## Known issues / unknowns

The installer is Fedora/Linux-first and intentionally does not package Chromium. Browser discovery/capability diagnostics remain the existing product responsibility. Privileged router install/uninstall remains separate because it crosses the root privilege boundary.

The release tree currently retains prior content-addressed Core releases rather than adding automatic release garbage collection; that is safe for rollback and is not required by P044 acceptance.
