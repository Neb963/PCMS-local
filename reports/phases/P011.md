## Objective

Prove the public module path end-to-end using a reference `.pcmsmod` and a resettable module UI without introducing a privileged first-party path.

## Implemented

- T011.1 — added a Core-owned `ModuleUiHost` with random session identity, runtime-generation binding, independent UI generations, explicit FAILED/reset lifecycle and stale-generation rejection.
- Module UI is mounted through a Core wrapper containing a sandboxed iframe with `sandbox="allow-scripts"` and deliberately no `allow-same-origin`. Raw module assets receive a restrictive CSP with no direct network access. The wrapper exposes the scoped semantic SDK through a bounded postMessage bridge rather than granting the module arbitrary Core API access.
- The module UI SDK endpoint is scoped to session/runtime generation, reuses the module SDK method allowlist and Core runtime-generation authorizer, validates bounded JSON, preserves the daemon Host/Origin boundary, and returns structured errors. A failed UI can be reset while `pcmsd` remains healthy.
- T011.2 — added an immutable module package store using the existing bounded `.pcmsmod` parser. Packages are staged privately and retained under module/version/content-digest paths; same-artifact installs are idempotent, version/digest conflicts fail closed, and extracted files are revalidated against the immutable archive including rejection of unexpected injected files/directories.
- Added a shared `ModuleManager` for install, update, approval/activation, active runtime startup and UI mounting. It uses the existing state, authority, activation and lifecycle stores and the real module runner. No first-party flag or privileged package path was added.
- Install/update candidates are started in the real isolated runner before activation. An unhealthy backend remains inactive and the last-known-good version remains runnable. State-schema-changing updates fail closed until an executable migration contract exists.
- Added a deterministic reference `.pcmsmod` fixture with backend, namespaced storage use and UI assets. Its 1.0.0 → 1.1.0 update, retained-version rollback, stale runtime fencing, disable/re-enable fencing and UI remount all use the shared package/runtime/UI path.
- T011.3 — added integration coverage for UI failure/reset, scoped SDK transport, update/rollback, disable/re-enable, package-tree integrity and unhealthy-update survival.

No Deployer/Refresher/Explorer/Provisioning/Statistics feature behavior and no Chromium Persona implementation was added.

## Deviations / ADRs

No architecture deviation and no new ADR.

The constrained UI host uses a sandboxed iframe without `allow-same-origin`. This is stricter than merely serving module UI under the Core origin and preserves the architecture rule that module UI cannot inherit arbitrary Core authority simply because it is local. The SDK bridge remains Core-owned and session/runtime-generation scoped.

The package store keeps owner-writable directories so deterministic cleanup, future purge and retained-version management remain possible. Package/archive files are read-only after publication, and every load reparses the immutable archive and verifies the extracted tree against it.

## Known issues / unknowns

- The shared update path currently accepts only state-schema-preserving package updates. A package that changes `stateSchemaVersion` fails closed because P011 does not define a package-carried executable migration contract.
- Failed/inactive candidate package artifacts are retained rather than silently deleted. Retention is conservative and supports evidence/rollback; a future explicit pruning policy may remove unreferenced artifacts.
- Module packages remain operator-trusted same-user executable code. The runner and UI host contain lifecycle/authority failures but are not an OS hostile-code sandbox.
- This phase deliberately does not use a real Chromium browser or MCP. Chromium Persona runtime begins in P012; generic DevTools acceptance is owned by P015 and final live MCP by P048.
