## Objective

Make remote mutation admission durable and duplicate-safe across crashes, cancellation and ambiguous dispatch without implementing module-specific provider mutation policy.

## Implemented

- T027.1 — appended immutable migration `0009-operation-coordinator` with Core-owned `operations` and `operation_target_epochs` state. Target epochs are retained independently from operation-history retention so fencing cannot reset if terminal detail is later compacted.
- T027.1 — added `OperationCoordinator` with stable PCMS target keys, atomic one-unresolved-claim admission, monotonic claim epochs, durable idempotency keys, bounded provenance/precondition evidence, owner/module runtime provenance, desired-state fingerprint metadata and legal state transitions.
- T027.1 — integrated unresolved module operation evidence with the existing module lifecycle guard. Module-owned operations survive runtime changes, while dispatch revalidates the exact enabled module version/runtime generation immediately before side-effect authority is issued.
- T027.1 — implemented stale-epoch fencing at every state transition/dispatch boundary. A completed claim releases the target, while the next claim increments the persistent target epoch.
- T027.2 — implemented fresh preflight enforcement immediately before dispatch authorization. Preconditions are timestamped, bounded and replaceable only while PREPARED; stale/future evidence cannot authorize mutation.
- T027.2 — dispatch authorization atomically changes PREPARED to RUNNING and persists dispatch timestamp plus bounded non-secret dispatch evidence before a side-effecting caller can receive a permit. From that boundary onward Core conservatively treats the effect as possibly dispatched unless explicit evidence proves otherwise.
- T027.2 — added execution-loss classification: browser/module/network/control-plane loss after possible dispatch becomes/remains UNCERTAIN; an explicit NOT_DISPATCHED outcome may become FAILED_SAFE only from RUNNING.
- T027.2 — wired `pcmsd` startup to recover persisted RUNNING/VERIFYING operations to UNCERTAIN before readiness. PREPARED work is not replayed merely because the daemon restarted, and unresolved claims remain blocking.
- T027.2 — cancellation now distinguishes pre-dispatch and post-dispatch state. PREPARED may become clean CANCELLED; RUNNING/VERIFYING cancellation becomes UNCERTAIN; cancellation of already uncertain/human-blocked work records intent without asserting remote rollback.
- T027.3 — added restart/cancellation/process-loss matrices covering browser loss, module loss, explicit non-dispatch, daemon restart, stale fencing, stale preflight, module runtime replacement and claim exclusion.
- T027.3 — added explicit regression proof that an UNCERTAIN operation cannot be dispatched again through the existing claim and cannot be bypassed by preparing a second operation for the same stable target.
- T027.3 — updated the P022 migration regression so it verifies immutable migration `0008-generator-identity` remains present instead of incorrectly requiring it to remain the final migration forever.

## Deviations / ADRs

No ADR change was required.

P027 stores the monotonic target fencing epoch in a dedicated Core table rather than deriving it from retained operation rows. This is a direct implementation of the architecture's monotonic fencing invariant and prevents future terminal-history compaction from accidentally resetting target authority.

Dispatch authorization is intentionally conservative: Core persists RUNNING before returning a dispatch permit. A crash in the narrow interval after permit persistence but before the external call therefore recovers as UNCERTAIN unless the caller can provide explicit NOT_DISPATCHED evidence. This favors duplicate-prevention over optimistic retry and matches the architecture's fail-closed doctrine.
