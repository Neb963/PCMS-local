## Objective

Persist Account/Persona entities and enforce one-active-account-to-one-dedicated-Persona with audited rebinding.

## Implemented

- T021.1 — appended immutable migration `0007-account-persona-inventory` with durable Account records, a nullable Account→Persona binding, revision/timestamp state, a partial unique index preventing two ACTIVE Accounts from sharing one Persona, and append-only binding-history storage.
- T021.1 — added a Core-owned `AccountRepository` for stable Account identity/display/lifecycle metadata and a read-only `PersonaRepository` projection over the existing authoritative Persona/profile-lifecycle table. Persona creation/profile ownership remains with the P012 lifecycle implementation.
- T021.2 — added `PersonaBindingService.bind` using one `BEGIN IMMEDIATE` transaction, active Account/Persona validation, expected Account revision fencing, structural Persona uniqueness, and atomic BIND history insertion.
- T021.2 — duplicate active Persona assignment is rejected without changing the losing Account or creating partial history; the SQLite partial unique index independently enforces the invariant if callers bypass the service.
- T021.3 — added explicit `rebind` and `unbind` operations with expected-revision fencing, non-empty bounded reasons and append-only BIND/REBIND/UNBIND history containing previous/next Persona IDs and resulting Account revision.
- T021.3 — added injected history-write failure coverage proving an Account rebind and its audit event are one transaction: when history insertion aborts, Account binding and revision roll back to their prior values.
- T021.3 — history UPDATE and DELETE are rejected by database triggers, preserving understandable binding provenance.

## Deviations / ADRs

No ADR change was required.

The existing P012 `personas` table remains the single authoritative Persona persistence record rather than creating a second inventory table. P021 adds only a read-only inventory projection over it; this preserves stable Persona/profile ownership and avoids competing identity sources.

Account lifecycle is intentionally minimal (`ACTIVE`/`INACTIVE`) in this phase. Provider/session operational state is not encoded into Account lifecycle, preserving the architecture distinction between durable lifecycle and temporary observed health.
