## Objective

Prove Deployer polling shares Core admission/backpressure, prove Deployer uses the ordinary updateable `.pcmsmod` lifecycle while Core-owned operation evidence survives runtime changes, and complete the Account→Persona→protected synthetic route→Perchance emulator→Deployer deterministic CI vertical slice.

## Implemented

- T033.1 — added `DeployerPollExecutor`, which consumes durable scheduler intents through the existing shared `ProviderGate`. Provider busy/cooldown never runs the poll callback; the queue claim is abandoned while the same durable pending dispatch remains available for a later scheduler wake.
- T033.1 — added a narrow scheduler acknowledgement for successful observation-only dispatches. It clears the pending dispatch only after the poll completes, preserves the schedule's already-advanced next-due time/budget semantics, clears stale failure state and completes the bounded queue item.
- T033.1 — regression coverage proves duplicate wake coalescing, exact dispatch-ID reuse after provider contention, provider-wide cooldown propagation and one actual poll execution per admitted dispatch.
- T033.2 — added a deterministic Deployer `.pcmsmod` package fixture with the real Deployer module ID, declared capability envelope, generic module-runner backend, namespaced storage and only semantic Core SDK calls.
- T033.2 — lifecycle acceptance installs Deployer 1.0.0, creates Core-owned unresolved operations, updates the package to 1.1.0 without a Core reinstall, fences the stale runtime, crashes the active runtime, disables/re-enables the module and rolls back to retained 1.0.0 state through a new runtime generation.
- T033.2 — Core `OperationCoordinator` target claims and module unresolved-evidence records survive update, crash, disable and rollback; the rolled-back runtime reads its last-known-good state rather than the 1.1.0 state.
- T033.3 — extended the synthetic protected SOCKS fixture with an optional explicit test-only forwarding target, while preserving the existing canned route-identity probe. Forwarded client bytes are captured so CI can prove provider API request lines traversed the protected tunnel even when Chromium reuses keep-alive connections.
- T033.3 — added a real-Chromium vertical acceptance that launches the bound Persona through a verified protected synthetic route, reaches the Perchance emulator only through the synthetic SOCKS forwarder, installs/runs Deployer through the normal module path, invokes deployment through a semantic SDK service, injects `RESPONSE_LOSS_AFTER_EFFECT`, reconciles the remote result read-first and independently verifies emulator state.
- T033.3 — the vertical acceptance also verifies current protected-route mutation admission immediately before the module's Core deployment service is invoked, and verifies the routed HTTP traffic contains every provider API call observed by the emulator.

## Deviations / ADRs

No ADR change was required.

Polling is intentionally not modeled as a remote mutation operation. The durable scheduler owns the poll intent, while the shared ProviderGate supplies cross-feature provider pressure. A poll callback is therefore safe to re-attempt after a local gate refusal or observation failure, and successful observation dispatch is acknowledged directly by the scheduler.

The Deployer package used for deterministic lifecycle acceptance is generated as a valid `.pcmsmod` fixture but runs through the actual package parser, ModuleManager, state generations, generic module-runner and SDK authority fencing. The test does not claim a final release-bundle distribution path; release artifact packaging remains later hardening scope.

The routed vertical test uses a synthetic SOCKS exit with an explicit allowlisted forwarding target to the local emulator. It does not weaken protected-routing fail-closed behavior: only the test-declared emulator hostname/port is forwarded, while route identity verification still uses the existing independent canned probe.
