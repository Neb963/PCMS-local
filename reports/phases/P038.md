## Objective

Validate provisioning inputs before side effects, allocate a dedicated persistent Persona for a staged Account, and drive signup/login against the same managed browser session without prematurely implementing challenge continuation, provider-identity activation or interrupted-flow recovery.

## Implemented

- T038.1 — added `src/provisioning/staging.ts` with full-batch normalization and duplicate detection before staged-state mutation. Account IDs and case-insensitive provider identities are checked across the incoming batch, existing Account IDs and already staged records before the batch is admitted.
- T038.1 — staged Accounts are explicitly INACTIVE. Credential material is represented only by an opaque bounded `credentialSecretRef`; staging never creates an Account, Persona or provider-side effect.
- T038.2 — extended `PersonaBindingService` with an explicit provisioning-only bind path for INACTIVE Accounts. Normal active-Account binding semantics are unchanged. Provisioning binding requires an ACTIVE Persona, optimistic Account revision, and exclusive ownership against every other managed Account, then records the ordinary append-only BIND history transactionally.
- T038.2 — added `ProvisioningAllocationService`, which creates/reuses the INACTIVE staged Account, allocates its persistent Chromium Persona through `PersonaProfileLifecycle`, and binds that exact Persona without activating the Account. Exact retries are idempotent.
- T038.3 — extended the deterministic Perchance emulator with browser-facing signup, login and session surfaces. Password bytes are accepted only as transient request input; emulator request evidence records only `passwordPresent`, never the password value.
- T038.3 — added `ProvisioningBrowserFlow` for transient signup/login browser operations. It operates through an existing `BrowserPage`, returns only safe provider/session observations, and labels the authenticated-session identity observation `UNVERIFIED` so P038 cannot accidentally satisfy P039's identity-activation gate.
- T038.3 — real-Chromium acceptance allocates the staged Account's Persona, drives signup and login in its existing page target, detaches and reattaches BrowserDriver, then proves PID, profile, page target and authenticated browser session remain the same while the Account remains INACTIVE.

## Deviations / ADRs

No ADR change was required.

Provisioning staging is intentionally process-local in P038. It establishes the pre-side-effect validation boundary but does not claim restart recovery; P039 explicitly owns interrupted signup/login recovery. Durable Account state begins when allocation is requested, and the Account remains INACTIVE until P039 proves provider identity.

The existing active-Account binding API was not weakened. A separate provisioning-only path permits an INACTIVE staged Account to reserve a Persona while applying a stricter exclusivity check against any other Account owner. This preserves the one-dedicated-Persona intent without conflating pre-activation provisioning with normal active Account operation.

The deterministic browser test uses headless Chrome for CI, but automation attaches to the exact persistent Persona process/profile/page that BrowserManager owns; no synthetic automation-only browser identity is created. The same code path supports the operator-visible non-headless Persona.

## Known issues / unknowns

- Provider identity observed after signup/login is deliberately marked UNVERIFIED and the Account remains INACTIVE. P039 owns authenticated provider-identity proof and activation.
- CAPTCHA, verification-code HumanTasks and interrupted/ambiguous signup reconciliation are deliberately not implemented here; they are P039 scope.
- Process-local staging itself is not restart durable. P039 recovery must reconstruct or durably represent the provisioning flow without storing raw credentials.
- Live Perchance signup/login behavior is not asserted here; P038 proves the deterministic emulator contract only. Final live provider acceptance remains reserved for P049.
