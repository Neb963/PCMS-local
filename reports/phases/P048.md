## Live-acceptance discrepancies and CI-first handling

1. **Chromium process-title argv rewrite (production defect).** Chrome for Testing 154 on this host rewrites `/proc/<pid>/cmdline` into a single space-joined entry shortly after startup, so the NUL-separated argv ownership check failed closed on every post-launch verification and close. Reproduced deterministically first (a child process setting `process.title` produces the identical cmdline form; `tests/unit/chromium-process-title.test.mjs`), then fixed by recognizing both forms with token-boundary matching so a longer sibling path can never match by prefix (commit `298d583`). A launch-time variant — a torn read racing the rewrite — was reproduced by the real-Chromium suite and fixed with a bounded evidence re-read at capture time only; the ownership checks themselves still fail closed (`3dceed9`).
2. **Pending CDP commands outliving their target (production defect).** A command already in flight to a target that is destroyed hung until its command timeout instead of being classified as target loss when `Target.targetDestroyed`/`Target.detachedFromTarget` was observed. Reproduced by `tests/browser/browser-driver.test.mjs` under load, then fixed: pending commands addressed to an observed-lost target are rejected as `BROWSER_DRIVER_TARGET_LOST` (`3dceed9`).
3. **Test-side timing assumptions.** Browser test helpers matched page targets by URL, but Chrome sets the target URL at navigation start, so the previous document could still be current; and fixed-delay cmdline/target-loss probes raced normal Chromium behavior under load. Fixed in the helpers (in-page `location.href` gating, full-load wait, NUL-normalized substring matching for flags that embed spaces, target-loss polling). No production behavior was relaxed.

No security boundary was weakened: protected routing still fails closed, browser ownership checks still fail closed (both got strictly more tolerant only in recognizing the process PCMS itself spawned), and no module/boundary rule was touched.

## Post-review correction (P048 reopened)

Closure review found one production regression in `3dceed9` and it was corrected before P049 opened:

- **`Target.detachedFromTarget` was treated as permanent target destruction.** That CDP event only says a *session* was detached; it occurs for an ordinary `Target.detachFromTarget` and can occur multiple times per target with multiple sessions, while the target stays alive. The handler added the target to the permanent lost set and rejected every pending command for it. Reproduced deterministically first: with only the new `BrowserPage.detach()` primitive in place, an ordinary detach rejected the in-flight detach command itself as "target disappeared" and poisoned the target against fresh attaches. The fix makes the event session-scoped — pending commands bound to the detached `sessionId` reject with a new `BROWSER_DRIVER_SESSION_DETACHED` code, later commands on that session fail fast at dispatch, and the target is never recorded as lost; permanent loss still comes only from `Target.targetDestroyed`. `BrowserPage.detach()` is retained as the supported non-destructive detach (spec 03 §9), a new deterministic regression test drives an ordinary detach with a second live session on the same target, and the target-loss test now asserts the refined contract (fast failure with a loss-classified code; which teardown event lands first decides `TARGET_LOST` vs `SESSION_DETACHED`).
- **Close-time transient evidence mismatch** (found while re-running the suite): one `/proc` evidence read during Chrome's teardown could observe a transient mismatch and fail an otherwise clean close. `waitForFingerprintGone` now tolerates a short bounded mismatch window while continuing to poll; the pid is never signalled while evidence is ambiguous and a persistent mismatch still fails closed.
- The reopen was recorded as an `IN_PROGRESS` checkpoint (`e5f6a2c`) before implementation. Disclosed imperfection: that checkpoint initially recorded a non-derived M12 milestone status and a non-canonical STATUS current-phase line, so the repository-contract job of runs **#739**/#740 failed; the contract-corrected planning state was published with the fix and run **#741** is fully green.
- The unrelated `plan.json` churn from the closure commit (a P033 arrow string rewritten to `\u2192` escapes by the JSON round-trip) was reverted; planning rewrites now preserve non-ASCII literally.
