## Objective

Implement deterministic Explorer candidate observation and claim semantics without treating provider availability as ownership, use Core operation safety for external claim effects, and hand verified acquisitions into stable Core Generator/Project identity without implementing Account Provisioning.

- T037.2 — added `src/explorer/claim.ts` using `OperationCoordinator`, stable Account target claims and the shared ProviderGate. Fresh verified availability is a mutation precondition, not proof of ownership.
- T037.2 — claim acknowledgement is insufficient for reservation. The service reads authenticated provider ownership and reserves only an exact verified slug/provider-stable-ID acquisition.
- T037.2 — response loss after provider effect is recorded through `OperationCoordinator.recordExecutionLoss` and reconciled read-first through `OperationReconciler`; automatic redispatch is blocked while the effect is ambiguous.
- T037.2 — completed claims can reconstruct process-local reservation evidence after restart from the durable SUCCEEDED operation plus fresh exact provider ownership. The recovery path uses a newly constructed coordinator and does not issue a second claim mutation.
- T037.3 — appended immutable migration `0014-project-targets` and added a minimal Core `ProjectRepository` containing only stable Project identity and its one-to-one Generator target. Rich Project/source/deployment policy remains outside Core.
- T037.3 — added `ExplorerHandoffService`, which requires a verified completed acquisition, then atomically creates/reuses stable Generator and Project rows. Provider stable identity is authoritative for the acquired Generator; mutable slug equality alone cannot collapse identities.
- T037.3 — handoff is idempotent for the same stable identities and rejects conflicting Generator or Project identity mappings.

## Deviations / ADRs

No ADR change was required.

Before acquisition there is no stable Generator identity, so Explorer uses the selected stable Account as the conservative Core operation target while the provider claim is unresolved. Candidate slugs remain mutable observation data and never become Core identity keys.

Explorer reservation evidence is intentionally not a second Core source of truth. A successful claim is durable in `operations`; if process-local reservation state is lost before handoff, it is reconstructed only from that completed operation plus fresh exact provider ownership. Stable Generator/Project records are created only after that verification.

The new Core Project schema is deliberately minimal, consistent with spec 17: Core owns stable cross-module Project identity, while richer source/deployment policy remains in the Deployer/project domain.

## Known issues / unknowns

- Current live Perchance Explorer availability/claim wire behavior is not asserted here; P037 proves the deterministic emulator contract only. Live provider acceptance remains reserved for P049.
