## Objective

Expose the smallest authenticated local Web UI and typed CLI/JSON client over the Core API, without implementing domain feature screens or allowing clients to access SQLite directly.

## Implemented

- T004.1 — added a per-install 256-bit local API token stored in the PCMS config root as a private `0600` regular file, exact bearer-token validation, strict loopback Host validation, same-origin Origin rejection, an authenticated `/api/v1/status` endpoint, and a minimal pcmsd-served Web UI shell. The shell uses CSP, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `nosniff`, no-store responses and no query-string secrets. The bootstrap token is embedded only in the same-origin HTML document; static assets do not contain it.
- T004.2 — added a typed loopback-only Core API client and `pcms status [--json]`. The CLI reads the same private local token and uses the same authenticated HTTP endpoint as the Web UI. JSON mode emits a stable envelope and failures remain structured without printing the token.
- T004.3 — added real-pcmsd integration coverage proving the UI shell loads from pcmsd, CSP/security headers are present, unauthenticated status requests are rejected, hostile Origin/Host requests are rejected, a correctly authenticated same-origin request returns typed Core status, static JS does not contain the token, and a separately spawned CLI process returns both stable JSON and human-readable status through that same API.

No Account/Persona/Generator/module APIs, domain feature screens, direct client database access, WebSocket/event transport, user-service integration or release bundle behavior was added.

## Deviations / ADRs

No architecture deviation. The phase implements architecture 10's approved "per-install high-entropy local token/session bootstrap" option and architecture 12's single logical control surface. The Web UI and CLI both call `/api/v1/status`; neither receives a direct SQLite handle.

The pre-existing narrow bootstrap `/api/v1/health`, `/api/v1/ready` and `/api/v1/version` endpoints remain loopback-only and read-only. The authenticated operator control surface introduced in P004 is `/api/v1/status`.

## Known issues / unknowns

- The Web UI is intentionally only a foundation shell; domain navigation/screens belong to later owning phases.
- The CLI intentionally exposes only `status` in this phase. Account/Persona/module/operation commands cannot exist correctly until their domain APIs exist.
- P004 does not add cookie/session authentication, WebSockets or mutations; future state-changing/cookie transports must continue to satisfy CSRF and origin requirements.
- P005 still owns user-systemd lifecycle and an installable development/release bundle skeleton.
