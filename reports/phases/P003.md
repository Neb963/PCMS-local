## Objective

Create the one authoritative SQLite adapter with required pragmas, ordered immutable migrations and incompatible-schema rejection, without adding Account, Persona, Generator, module or other domain repositories.

## Implemented

- T003.1 — added the authoritative `pcms.db` path under the PCMS data root and a file-backed `node:sqlite` connection adapter configured for foreign-key enforcement, WAL journaling, a bounded 5000 ms busy timeout, disabled loadable extensions, `trusted_schema=OFF`, and defensive mode when supported by the pinned runtime.
- T003.2 — added centrally ordered Core migration definitions, SHA-256 migration checksums, PCMS application identity (`0x50434d53`), SQLite `user_version` authority, exact migration-history verification, transactionally applied migrations, rollback on migration failure, and rejection of changed/gapped/unknown migration history.
- T003.3 — added the pcmsd database bootstrap boundary so HTTP readiness is exposed only after the authoritative database opens and migrates successfully. Added deterministic integration coverage for fresh creation, ordered upgrade, failed-migration rollback, foreign application identity, unsupported newer schema, unowned non-empty databases, corrupt database bytes, and daemon lock cleanup after database bootstrap rejection.

No Account/Persona/Generator/module domain tables or repositories, Web UI, CLI feature surface, browser management, provider behavior or routing adaptation was added.

## Deviations / ADRs

No architecture deviation. The phase implements architecture 02's preferred built-in SQLite adapter behind an internal boundary and preserves the startup order established by architecture 01: single-instance ownership is acquired before the database is opened/migrated, and API readiness follows successful database bootstrap.

Only the migration-authority metadata table (`schema_migrations`) is introduced. Domain tables intentionally remain for later owning phases rather than being speculatively created here.
