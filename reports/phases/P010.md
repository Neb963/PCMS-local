## Objective

Complete destructive/lifecycle controls without losing module state or unresolved operation evidence.

## Implemented

- T010.1 — added Core-owned module lifecycle state (`ENABLED`, `DISABLED`, `REMOVED`) through immutable migration `0004-module-lifecycle-evidence`. Existing disabled registrations migrate to `DISABLED`.
- Added durable module lifecycle evidence references for unresolved `OPERATION` and `HUMAN_TASK` records. This is deliberately a narrow retention/guard bridge for future OperationCoordinator/HumanTask implementations, not an early implementation of those domains.
- Disable/re-enable transitions are idempotent, use expected runtime generation, increment generation only on a real transition, fence stale runtimes, and preserve active module state plus all unresolved evidence.
- T010.2 — added rollback to a previously activated `RETAINED` state/version generation. Rollback verifies prior activation authority, atomically retains the current generation, promotes the target, restores its version/schema/approved authority, resets the active revision and increments runtime generation. No stale module process is reused.
- T010.3 — added default remove semantics that fence the runtime and mark the registration `REMOVED` while retaining state, authority history and lifecycle evidence.
- Purge requires explicit confirmation, requires prior remove, and fails closed while any unresolved operation/HumanTask evidence exists. After all evidence is resolved, purge deletes the registration, state generations, state entries, authority records and lifecycle evidence transactionally.
- Final review hardened legacy P008 runtime-generation fencing so it synchronizes lifecycle status and cannot resurrect a removed module. P009 candidate activation now also rejects `REMOVED` modules.

No feature-specific module behavior, full OperationCoordinator/HumanTask domain model, module UI host or reference-package installation flow was implemented.

## Deviations / ADRs

No architecture deviation and no new ADR.

Because the full OperationCoordinator and durable HumanTask repositories are owned by M06, P010 introduces only `module_lifecycle_evidence`: durable references identifying unresolved Core evidence that still requires a module. Future operation/task code can register and resolve those references without coupling module purge logic to its schema internals.

Rollback reuses the retained immutable state generation but always creates a **new runtime generation**, matching the architecture requirement that rollback never reuses a stale runtime process/generation. Physical reference-package installation/retention is exercised in P011; P010 governs the retained version/state lifecycle metadata needed for safe rollback.

## Known issues / unknowns

- P010 does not implement the full OperationCoordinator or HumanTask schemas; their later owners must integrate with the lifecycle evidence reference contract when creating/resolving module-dependent records.
- P010 does not implement module UI hosting or a real reference `.pcmsmod` installation/update flow; P011 owns that end-to-end public path.
- Default remove preserves recoverable registration/state/evidence in `REMOVED` status. Physical package-retention policy will become concrete once package installation inventory is exercised by P011.
