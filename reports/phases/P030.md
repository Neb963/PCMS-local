## Objective

Resolve an exact repository commit into bounded, validated deployment artifacts deterministically, without mutating Perchance or guessing ambiguous versions/layouts.

## Implemented

- T030.1 — added an explicit `GitHubReadAdapter` boundary and `ExactCommitRepositoryScanner`. The scanner accepts only full lowercase 40-character commit SHAs, requires the adapter to return that same commit, rejects truncated recursive trees, validates bounded normalized repository paths/object SHAs, sorts the exact file snapshot deterministically and binds blob reads to commit/path/blob SHA.
- T030.1 — repository tree and artifact byte limits are explicit. Oversized blob metadata remains visible in the exact snapshot so a matching deployment candidate fails as oversized instead of silently disappearing from discovery.
- T030.2 — added a Deployer-specific bounded ZIP parser rather than changing the existing .pcmsmod parser. It enforces archive/entry/uncompressed/compression-ratio/path bounds, CRC32, local/central metadata agreement, normalized paths, duplicate/path-conflict rejection, ZIP64/multi-disk rejection and special-file/link/device rejection.
- T030.2 — artifact layout is an explicit caller policy: `ROOT` requires declared files at archive root, while `SINGLE_DIRECTORY` requires exactly one top-level content directory. Required paths are explicit and bounded; there is no heuristic flattening.
- T030.2 — SHA-256 is computed over the original immutable ZIP bytes and returned with the parsed artifact.
- T030.3 — added `DeploymentArtifactResolver` over the exact repository scanner. Discovery is limited to direct children of an explicit repository directory using the explicit `<artifactName>-<semver>.zip` naming contract; unexpected ZIP names in that directory fail rather than being ignored as possible versions.
- T030.3 — selection is explicit: `EXACT`, `HIGHEST` or `ONLY`. EXACT never falls back; ONLY requires one candidate; HIGHEST uses SemVer precedence and rejects equal-precedence alternatives such as differing build metadata instead of choosing arbitrarily.
- T030.3 — only the selected repository blob is downloaded/validated. The resolved artifact records repository/commit/tree/path/blob provenance, semantic version, content SHA-256, content root and validated ZIP entries/files.

## Deviations / ADRs

No ADR change was required.

The current architecture does not prescribe a legacy repository ZIP filename or content-root convention. P030 therefore does not import one from earlier PCMS implementations. Instead, discovery policy explicitly supplies repository directory, artifact name, ZIP layout and required files. Version filenames use a narrow deterministic `<artifactName>-<semver>.zip` contract inside that explicitly selected directory.

The GitHub boundary is an adapter contract rather than direct unaudited HTTP access from Deployer logic. This preserves the architecture requirement that Deployer uses a GitHub read adapter and leaves transport/auth implementation behind the approved module/Core capability boundary.

The existing .pcmsmod ZIP parser was intentionally not generalized/refactored in this phase. Deployment artifacts have a different semantic contract; keeping validation separate avoids destabilizing already-proven module package lifecycle behavior.

## Known issues / unknowns

- P030 discovers and validates repository artifacts only; it does not map repository names/slugs to GeneratorRef or provider identity. P031 owns that boundary.
- The GitHub read adapter transport/auth implementation is not part of P030; the scanner contract is suitable for the approved `github.read` capability path.
- HIGHEST selection follows SemVer precedence only when explicitly requested. Build metadata does not affect precedence, so equal-precedence top candidates fail as ambiguous.
- Artifact naming/layout policy is explicit configuration. No automatic repository-layout guessing or legacy convention fallback is implemented.
- P030 does not persist Project/deployment history or perform provider writes.
