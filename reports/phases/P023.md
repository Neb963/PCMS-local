## Objective

Expose useful inventory, search and Account-to-Persona navigation while keeping configured, observed, verified, stale and unknown operational facts distinct.

## Implemented

- T023.1 — added Core-owned route, session and Account health projection types and functions. Route projections distinguish configured intent from observed state and verified state, carry explicit evidence timestamps/age, and mark evidence current, stale or unknown. Session projections separately represent observed versus verified provider identity and reject structurally ambiguous evidence.
- T023.1 — Account health derives conservatively from Account lifecycle/binding plus route/session projections. Unbound/inactive/stale/degraded/unknown/observed/healthy states remain explicit; verified provider identity mismatch degrades health rather than being inferred away.
- T023.2 — added `InventorySearchService` over Accounts, Personas and Generators using stable entity IDs as returned identity even when the match came from mutable display metadata, provider stable ID or Generator slug. Wildcard-looking input is treated literally, query length/result count are bounded, and deterministic ordering prefers exact stable-identity matches.
- T023.3 — added `InventoryReadService` and authenticated Core API endpoints for Account inventory, stable metadata search and Account→bound-Persona resolution. Bound Persona navigation resolves the stored `persona_uid` and returns bounded Persona metadata; it does not infer identity from display/session labels.
- T023.3 — extended the typed loopback API client plus CLI commands `pcms accounts list`, `pcms accounts persona <account-id>`, and `pcms search <query>`, including JSON forms.
- T023.3 — extended the same-origin Web UI with Account inventory, inventory search, and an “Open bound Persona” action that resolves through the Account stable ID and Core binding. The bearer token remains bootstrap metadata only and is not embedded in served JavaScript.

## Deviations / ADRs

No ADR change was required.

Health is deliberately modeled as a projection over explicit evidence rather than as a synthesized durable “truth” field. Configured route intent cannot satisfy verified protected-route health, and observed authenticated-looking state cannot become verified provider identity. Stale evidence remains identifiable by timestamp and age.

Search uses SQLite substring matching rather than introducing FTS infrastructure at this scale. Stable local entity IDs are always returned separately from mutable labels/slugs, following the architecture requirement that search metadata never become identity.

The daemon now exposes its already-open SQLite connection through the internal `PcmsDatabase` handle so Core read services can share the authoritative connection instead of opening a second writer-capable connection. This remains inside the Core/storage boundary and does not expose SQLite through public/module interfaces.
