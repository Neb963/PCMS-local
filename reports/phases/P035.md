## Objective

Implement Refresher-owned cohort, local-calendar active/sleep and budget policy while reusing Core's existing stable target claims and shared ProviderGate rather than creating competing mutation-admission machinery.

## Implemented

- T035.1 — added `src/refresher/policy.ts` with bounded deterministic cohort selection over stable Generator IDs. Explicit configured cohort size is limited only by the eligible managed pool, not by observed recent-page capacity.
- T035.1 — deterministic fairness ordering uses rotation debt, least-recent/never-cohorted preference, priority weight and stable Generator ID tie-breaking.
- T035.2 — added an explicit IANA-timezone daily active-window policy with configurable local start, active duration and independent daily mutation budget.
- T035.2 — budget state carries a durable/serializable UTC high-water observation. Wall-clock rollback uses the high-water instant instead of reopening an earlier local period; forward jumps move directly to the current local calendar day without replaying missed intervals.
- T035.2 — spring-forward missing wall time and fall-back repeated wall time are evaluated from timezone-aware local calendar parts. Repeated DST wall time does not reset the daily budget.
- T035.2 — uncertain refresh work can reserve budget until reconciliation; confirmed and released outcomes update the explicit policy state rather than consulting eventual analytics.
- T035.3 — added `RefresherAdmission`, which prepares Refresher mutation intent through the existing `OperationCoordinator` and the same `generatorOperationTargetKey(...)` used by Deployer. A same-Generator unresolved Deployer claim therefore blocks Refresher before dispatch.
- T035.3 — Refresher provider mutation admission delegates to the existing shared `ProviderGate`; no second concurrency/cooldown authority was introduced.
- T035.3 — added bounded Perchance gate-signal normalization for known `too-many-requests` and `captcha-needed` semantics. Rate limit is conservatively provider-wide; challenge is account-scoped. Cooldown durations remain explicit caller policy rather than invented provider timing.
- T035.3 — extended the deterministic Perchance emulator with `RATE_LIMIT` save rejection and challenge save rejection so cross-module gate propagation can be proved without live provider credentials.

## Deviations / ADRs

No ADR change was required.

P035 deliberately keeps Refresher policy outside Core. Core remains authoritative only for the generic scheduler, target claim and provider gate. The Refresher policy state is explicit and serializable so the standard module state/lifecycle mechanism can own persistence in P036 without moving feature policy into pcmsd.

The provider-signal mapping consumes only known semantic statuses. Unknown provider statuses do not invent a cooldown classification; the underlying provider mutation remains fail-closed under its existing adapter contract.

The observed recent-page capacity is accepted only as cohort diagnostics. It never becomes a cohort-size ceiling.
