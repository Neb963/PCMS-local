## Objective

Map an exact desired repository artifact to the managed stable Account/GeneratorRef target, revalidate current provider identity immediately before mutation, and prove the first safe emulator deployment through the shared OperationCoordinator.

## Implemented

- T031.1 — added `DeployerTargetResolver`. Repository slug is only a discovery key scoped to the stable Account; the resolver refuses missing/ambiguous mappings and refuses any Generator without a stable provider ID.
- T031.1 — the resolved Account must be ACTIVE and bound to a Persona. The existing Perchance identity probe is then run freshly and the target is accepted only when the expected session, stable provider ID and current slug all match. Stable-ID mismatch, slug drift and slug-only targeting fail closed before mutation.
- T031.2 — extended the Perchance adapter with bounded deployment save/read contracts. Desired artifact SHA-256, normalized file content and required public state are validated; session material stays in the browser page and is not returned to Core/log evidence.
- T031.2 — added `InitialDeploymentService`, which prepares a durable OperationCoordinator record before external effect, claims the stable `perchance:generator:<generatorLocalId>` target, records exact GitHub/artifact provenance, acquires the shared ProviderGate, revalidates dispatch preconditions and performs exactly one initial save.
- T031.2 — mutation outcomes are conservative: known provider rejection is recorded as proven non-dispatch; transport/protocol ambiguity is recorded as possible effect and therefore UNCERTAIN rather than blindly retried.
- T031.2 — extended the deterministic Perchance emulator with save/public deployment state keyed by stable provider `publicId`, plus bounded direct state inspection for acceptance evidence.
- T031.3 — after save acknowledgement, the service independently reads provider state and marks the operation SUCCEEDED only when stable ID, current slug, artifact SHA-256, exact files and required public state match desired state. Read failure or mismatch becomes UNCERTAIN.
- T031.3 — the real-Chromium emulator acceptance additionally reads emulator state directly, proving the persisted desired content/public state independently of the adapter's post-save verification path and asserting only one save request occurred.

## Deviations / ADRs

No ADR change was required.

The architecture defines the provider adapter boundary and reserves real Perchance compatibility for final live acceptance; it does not freeze the raw current Perchance save payload. P031 therefore models the narrow save/read surface in the adapter and deterministic emulator, using the predecessor evidence available to the project. This is not claimed as current live-provider compatibility; P049 owns that proof.

The current Account domain does not persist a provider login identity string. P031 therefore receives the expected provider identity from the caller and proves that the page-local authenticated session and stable Generator ownership match it before dispatch, without adding an unrelated Account schema change.

P031 does not add a new routing subsystem or duplicate route admission inside Deployer. The managed Persona/browser and shared operation/provider admission seams remain authoritative; the full Account→Persona→synthetic-route→emulator vertical slice is explicitly owned by P033.
